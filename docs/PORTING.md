# Портирование QEMU на iOS 6 / ARMv7

Заметки о том, почему сборочные скрипты выглядят именно так. Почти всё
здесь — следствие одной комбинации: **очень новый компилятор и очень старый
SDK**. Xcode 26 про armv7 всё ещё знает и код под него генерирует, а
заголовки и стабы iPhoneOS 6.1 застали далеко не всё, на что современный
clang рассчитывает.

## Почему именно SDK 6.1

Начиная примерно с iOS 11 Apple убрала armv7-срезы из стабов libSystem, так
что слинковать 32-битный бинарник против современного SDK физически нельзя.
Нужен SDK той эпохи. Из доступных вариантов 6.1 — ровно версия целевого
устройства, и это дополнительная страховка: в него нельзя случайно позвать
API, которого на iPhone 4S не окажется.

## TLS: почему деплоймент-таргет 9.0

QEMU использует `__thread` (`tcg_ctx`, `current_cpu`, RCU) — без него
configure просто отказывается продолжать. А clang включает поддержку TLS для
32-битного iOS-устройства только с деплоймент-таргета 9.0; в
`DarwinTargetInfo` это записано буквально:

```
если 64 бита           -> TLS с iOS 8
если 32 бита, железо   -> TLS с iOS 9
если 32 бита, симулятор-> TLS с iOS 10
```

Понизить планку флагом нельзя, а голый триплет без «ios» в эту ветку вообще
не попадает и остаётся с выключенным TLS — то есть ломается так же, просто
по другой причине.

Отсюда схема: QEMU компилируется и линкуется с триплетом
`armv7-apple-ios9.0`, но с `-femulated-tls`, чтобы обращения к TLS шли через
вызовы рантайма, а не через нативные Mach-O TLV, которых dyld на iOS 6 не
понимает. После линковки `vtool -set-build-version ios 6.0` возвращает
библиотеке настоящий минимум — иначе dyld на устройстве откажется грузить
библиотеку, «требующую iOS 9».

Важно: `CFLAGS` и `LDFLAGS` должны нести один и тот же `-target`. configure
склеивает их в одну команду clang для своих проверок, и из нескольких
`-target` побеждает последний — разъехавшись, они молча заставят проверки
компилироваться не под тот таргет, что настоящая сборка.

`__emutls_get_address` живёт в compiler-rt, но armv7-срез из
`libclang_rt.ios.a` в современных Xcode убран, поэтому реализация лежит в
`scripts/compat/ios6-compat.c`.

## Чего нет в SDK 6.1

| Что | Кто использует | Решение |
|---|---|---|
| `clock_gettime`, `CLOCK_MONOTONIC` | `include/qemu/timer.h`, безусловно | заглушка через `mach_absolute_time()` в `ios6-compat.h`, подключается через `-include` |
| `VM_FLAGS_RANDOM_ADDR` | `accel/tcg/translate-all.c` | константа ABI ядра, объявлена там же |
| `fdopendir` | `hw/usb/dev-mtp.c` | `CONFIG_USB_STORAGE_MTP=n` — проброс каталога хоста нам не нужен |
| `__clear_cache` | `tcg/arm/tcg-target.h` через билтин | реализован через `sys_icache_invalidate()` |
| заголовки libc++ | `disas/libvixl` | C++ отключён целиком, см. ниже |
| `libproc.h` | `glib/gspawn.c` | блок скрыт под `A5_IOS_BUILD` |

## Как отключается C++

`disas/libvixl` — дизассемблер AArch64 на C++, который configure включает
для любого ARM-хоста независимо от `--target-list`. Ему нужны настоящие
заголовки libc++, а искать современные и подсовывать их старому sysroot —
верный способ получить несовместимость ABI уже на устройстве.

В configure включение libvixl обусловлено наличием C++-компилятора:

```
arm)
  disas_config "ARM"
  if test -n "${cxx}"; then
    disas_config "ARM_A64"
  fi
```

а сам `cxx` обнуляется, если команда не находится. Поэтому
`--cxx=a5-no-cxx-compiler` убирает из сборки весь C++ разом. Теряется при
этом только дизассемблер A64 на armv7-хосте — то есть ничего.

## Прочие особенности configure

* **Корутины.** Для iOS configure по умолчанию выбирает бэкенд
  `libucontext` — вендоренный сабмодуль, который на деле является
  реализацией под Linux/glibc и Darwin-кода не содержит вовсе.
  `--with-coroutine=sigaltstack` — портируемый POSIX-вариант, который
  configure для Дарвина и так принимает.
* **PIE.** Для iOS `pie` не задан, и configure добавляет `-pie` в LDFLAGS.
  С `-dynamiclib` это ошибка компоновки («-pie can only be used when
  linking a main executable»), поэтому нужен `--disable-pie`, а `-fPIC`
  передаётся явно.
* **Сабмодули.** Из полутора десятков нужен ровно один —
  `ui/keycodemapdb`, из него генерируются таблицы кодов клавиш. Остальные
  (`capstone`, `slirp`, `dtc`, `libucontext`, `roms/*`) либо отключены
  ключами, либо не участвуют в сборке `i386-softmmu`.
* **Аудио.** Ветка iOS в configure сама выставляет пустой список
  аудиодрайверов; передавать `--audio-drv-list` не нужно и нельзя.
* **Старый C.** clang 16+ считает ошибками неявные объявления функций,
  подразумеваемый int и смешение указателей. Ни libffi 3.3, ни pixman 0.40,
  ни QEMU 5.1 под это не писались, поэтому для стороннего кода прежний
  статус предупреждений возвращается флагами (см. `A5_LEGACY_C_FLAGS`).

## JIT

configure для iOS всегда включает `CONFIG_IOS_JIT`, а в `tcg/arm/tcg-target.h`
`flush_dcache_range()` под этим флагом — незаконченная заглушка с голым
`#error` в теле. Заменяется на `sys_dcache_flush()`.

Сам механизм двойного отображения (`alloc_jit_rw_mirror` через
`mach_vm_remap`) нужен на iOS 11+, где RWX-память запрещена. Он включается
свойством акселератора `mirror-rwx`, по умолчанию выключенным, — то есть на
jailbreak-устройстве с пропатченным ядром используется обычная RWX-память.
Если окажется, что ядро её не даёт, включается через
`-accel tcg,mirror-rwx=on`.

## Как всё связано с приложением

Приложение **не линкуется** с `libqemu-system-i386.dylib`. Причины две:

1. `qemu_init()` в одном загруженном образе можно вызвать ровно один раз —
   после остановки ВМ глобальное состояние QEMU остаётся грязным. Свежая
   копия dylib по новому пути даёт dyld основание считать её другим образом,
   со своими нулевыми глобалами.
2. Сборка приложения перестаёт зависеть от сборки QEMU, а неудачная
   загрузка библиотеки превращается из краха в dyld до `main()` во внятное
   сообщение на экране.

Мост (`bridge/a5_qemu.c`) компилируется **внутри** дерева QEMU и виден
приложению только через узкий C-ABI из `bridge/a5_qemu.h`. Это осознанный
отказ от практики «объявить структуры QEMU вручную на стороне приложения»:
при несовпадении layout такой код не падает на компоновке, а тихо портит
память.
